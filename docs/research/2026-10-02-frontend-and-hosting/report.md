# Own the server, borrow the edges

**The team should build its own thin web server for deep_reasoner and use OpenHands and ACP only at the edges.** The server would be FastAPI behind UW NetID sign-in. It would store per-user config rows that hold YAML, run a credential broker, and give each user a separate worker, while model-written code keeps running in Daytona. Piggybacking on OpenHands would not spare the team the security work it hopes to avoid. Open-source OpenHands is officially single-user: one shared API key, with settings and secrets shared by everyone on a backend. Its login, RBAC and per-user sandbox code ships under a PolyForm Free Trial license capped at 30 days a year. Its isolation never reaches deep_reasoner's REPL, and its web UI would flatten the agent tree and offers no in-conversation side panel. Dean's ACP instinct is right for the *agent* boundary. A small `dr acp` stdio adapter would put deep_reasoner into Zed, JetBrains and OpenHands Agent Canvas, and it is the cheapest way to try OpenHands locally. ACP is the wrong *browser* protocol today, though. Its only normative transport is stdio, its HTTP/WebSocket transport is still an Active RFD that does not replay missed messages, it has no notion of a user, and sub-agent sessions landed only as unstable schema on 30 September 2026. For the browser, AG-UI 1.0, stable since late September with first-class sub-agent events, paired with assistant-ui's nested-thread rendering is the closest ready-made fit, with plain REST for the side panel. Ship the localhost app first. Then run a closed hosted beta in which only Daytona executes model code and user keys never enter any environment the model can reach. Three unknowns decide the details, and a two-week spike should settle them: whether assistant-ui really renders a deep, concurrent deep_reasoner tree well, what UW IT offers for sign-in and hosting, and how much per-user process isolation the team is willing to operate.

## OpenHands leaves the hard multi-user work undone

The OpenHands of October 2026 is not the project most people picture. On **27 July 2026** the flagship repository was cleared and replaced by **Agent Canvas**, a React/TypeScript front end and launcher. Agent execution, the event model and the canonical REST/WebSocket API now live in the separate Python `software-agent-sdk` and its agent-server ([OpenHands README](https://github.com/OpenHands/OpenHands/blob/main/README.md); [PR #15397](https://github.com/OpenHands/OpenHands/pull/15397)). The V0 runtime and agenthub stack that most blog posts describe was removed in April 2026 ([PR #13952](https://github.com/OpenHands/OpenHands/pull/13952)). The pace of change is relentless. The SDK went from 1.0.0 (7 November 2025) to **1.50.1 (30 September 2026)**, and Canvas shipped **19 tagged releases between 24 July and 25 September** ([SDK tags](https://github.com/OpenHands/software-agent-sdk/tags); [OpenHands tags](https://github.com/OpenHands/OpenHands/tags)). The CLI's ACP mode was promised "full support indefinitely" in June, then declared "no longer actively maintained" on 11 August ([transition FAQ](https://github.com/OpenHands/docs/issues/657); [OpenHands-CLI README](https://github.com/OpenHands/OpenHands-CLI/blob/main/README.md)). Anything built against OpenHands internals is built against a moving target.

The reason to piggyback was to inherit security, and the open-source edition does not have it. The official FAQ says OpenHands "is not appropriate for multi-tenant deployments where multiple users share the same instance. There is no built-in authentication, isolation, or scalability" ([OpenHands FAQ](https://docs.openhands.dev/overview/faqs)). The official Helm chart calls Agent Canvas "an **unauthenticated, single-tenant** application" in which "all agents are comingled on the same pod" ([Helm README](https://github.com/OpenHands/OpenHands/blob/main/helm/agent-canvas/README.md)). Access control is a list of session API keys that exists "to enable key rotation," not to identify users ([agent-server config.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-agent-server/openhands/agent_server/config.py)). Settings, LLM configuration and MCP servers are "scoped to the active backend" ([Backends docs](https://docs.openhands.dev/openhands/usage/agent-canvas/backends)), and custom secrets are "automatically exported as environment variables in the agent's runtime environment" ([Secrets docs](https://docs.openhands.dev/openhands/usage/settings/secrets-settings)).

On a shared UW instance, every beta user would effectively be an administrator of everyone else's keys and conversations. The two open proposals to add authentication to the open-source edition put multi-tenant isolation and SSO explicitly out of scope; they aim at a **single owner** per agent-server ([RFC #17055](https://github.com/OpenHands/OpenHands/issues/17055); [#17635](https://github.com/OpenHands/OpenHands/issues/17635)). Accounts, Keycloak/SAML login, RBAC and per-user sandboxes live in `OpenHands/enterprise` and `OpenHands-Cloud`. Both are under the **PolyForm Free Trial license, which says "Usage is limited to 30 days per calendar year without a commercial license"** and forbids redistribution ([enterprise README](https://github.com/OpenHands/enterprise); [LICENSE](https://github.com/OpenHands/enterprise/blob/main/LICENSE)). The research found no academic licensing program. The realistic open-source shape is therefore one agent-server per user behind an SSO proxy and router that the team writes itself. That is exactly the tenancy layer the team hoped not to build.

Sandboxing does not transfer either, because deep_reasoner's dangerous step happens where OpenHands cannot see it. Model-written Python runs inside deep_reasoner's own REPL backend. OpenHands' tool-level Docker mode isolates only OpenHands' built-in tools, and "tools without a Docker execution adapter continue to run in the outer Agent Server process" ([Docker execution docs](https://docs.openhands.dev/openhands/usage/agent-canvas/backend-setup/docker-execution)). When OpenHands drives an external ACP agent, it advertises no file-system or terminal capabilities, and "permission requests from the server are automatically granted" ([ACP agent guide](https://github.com/OpenHands/docs/blob/main/sdk/guides/agent-acp.mdx)). So deep_reasoner keeps doing its own sandboxing regardless. The Daytona runtime that V0 offered has no V1 equivalent ([openhands-workspace](https://github.com/OpenHands/software-agent-sdk/tree/main/openhands-workspace/openhands/workspace)). OpenHands' one real contribution is its per-conversation container mode (`OH_CONVERSATION_RUNTIME=docker`), which would wrap each deep_reasoner subprocess in its own container ([README](https://github.com/OpenHands/OpenHands/blob/main/README.md)). But that mode needs Docker access on the host, which users describe as "essentially equivalent to granting root control of the host" ([software-agent-sdk#1563](https://github.com/OpenHands/software-agent-sdk/issues/1563)). And it separates conversations, not one user's secrets from another's.

The UI fit is partial at best. Agent Canvas accepts "any stdio ACP server" through a **Custom** agent setting, with credentials passed in as global secrets ([ACP_AGENTS.md](https://github.com/OpenHands/OpenHands/blob/main/docs/ACP_AGENTS.md)). A deep_reasoner ACP adapter would therefore get chat, REPL cells rendered as "Run" cards, cost and cancel, with no OpenHands changes. However, the bridge keeps exactly one terminal event per tool call and silently drops plans, command and mode updates, and all sub-agent structure. Its `ACPToolCallEvent` has no parent field, and the Canvas renderer accepts only a closed union of OpenHands event types ([acp_agent.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/agent/acp_agent.py); [openhands-event.ts](https://github.com/OpenHands/OpenHands/blob/main/src/types/agent-server/core/openhands-event.ts)). Canvas Apps, the official UI extension point, can add a left-rail page. But the beta "does not support conversation tabs, arbitrary interface slots… or direct Agent Server WebSocket connections," and its API "may change" ([Canvas Apps docs](https://github.com/OpenHands/docs/blob/main/openhands/usage/agent-canvas/canvas-extensions.mdx)). The word "plugin" in OpenHands means a Claude-Code-style bundle of skills, hooks, MCP servers and sub-agent prompts; a plugin cannot replace the agent loop ([plugins guide](https://github.com/OpenHands/docs/blob/main/sdk/guides/plugins.mdx)). A deeper integration, a custom `AgentBase` subclass loaded into the agent-server, is technically possible. But Canvas can launch only the agent kinds `openhands` and `acp` ([api_models.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/settings/api_models.py)), and that route would tie deep_reasoner to a frozen pydantic schema that changes weekly.

**The verdict on direction (a): do not build the UW server on OpenHands.** Keep it for two cheaper uses. It is a **localhost experiment** that needs no UI code once `dr acp` exists. It is also a **pattern library**: its session socket (marked PROVISIONAL), for example, frames events as `Durable` and `Delta` messages with `after_seq` reconnect replay, which is exactly what a long-running deep_reasoner web run needs ([session_protocol.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-agent-server/openhands/agent_server/session_protocol.py)). Revisit this only if All Hands offers UW an academic Enterprise license. That would buy SSO, RBAC and isolated sandboxes, at the cost of a commercial dependency.

## ACP belongs at the agent edge, not the browser

The Agent Client Protocol is a healthy standard for the job it was designed for: an editor launching a trusted agent subprocess. Zed announced it in August 2025. It is now co-governed by Zed and JetBrains, who describe themselves as "working toward transitioning to an independent foundation" ([Governance](https://agentclientprotocol.com/community/governance)). Stable v1 is JSON-RPC 2.0 and has grown through additive RFDs, including session list and resume, a `usage_update` that carries cost, elicitation, and tool-call names. A v2 draft has been public since 20 July 2026 ([Updates](https://agentclientprotocol.com/updates); [v2 Draft](https://agentclientprotocol.com/announcements/acp-v2-draft)). Official SDKs exist for Python (`agent-client-protocol` 0.12.1 stable, 1.0.0rc2), TypeScript (1.6.0) and Rust. **About 40 agents** are listed, and clients include Zed, JetBrains IDEs, Neovim, Emacs and marimo ([PyPI](https://pypi.org/project/agent-client-protocol/); [Agents](https://agentclientprotocol.com/get-started/agents); [Clients](https://agentclientprotocol.com/get-started/clients)). Its vocabulary maps cleanly onto a REPL agent:

| deep_reasoner | ACP |
|---|---|
| think | `agent_thought_chunk` |
| REPL cell | `tool_call` of kind `execute`, with the code as `rawInput` and the observation as text content |
| FinalAnswer | `agent_message_chunk` plus `stopReason: end_turn` |
| namespaces | `select` config options |
| decompositions | slash commands |
| `input()` | elicitation |

Sources: [Tool Calls](https://agentclientprotocol.com/protocol/v1/tool-calls); [Config Options](https://agentclientprotocol.com/protocol/v1/session-config-options); [Slash Commands](https://agentclientprotocol.com/protocol/v1/slash-commands). Writing deep_reasoner as an ACP agent is cheap, and it would immediately work in every one of those clients, including OpenHands Agent Canvas.

As the wire protocol between a browser and a multi-user UW server, though, ACP fails on the properties that matter most.

**Only stdio is a normative transport so far.** The Streamable HTTP and WebSocket RFD has been "Active", not Completed, since 2 July 2026. It states that "in-flight messages are not replayed," defers replay and resumable streams to v2, and calls authentication "orthogonal" ([Transports](https://agentclientprotocol.com/protocol/v1/transports); [transport RFD](https://agentclientprotocol.com/rfds/streamable-http-websocket-transport)).

**The protocol has no notion of user, tenant or authorization.** Its stated design principle is a code editor talking "to a model you trust" ([Architecture](https://agentclientprotocol.com/get-started/architecture)).

**The agent tree, deep_reasoner's most distinctive feature, is the least settled part.** Stable v1 can only flatten sub-agents into the parent. The Subagent Sessions RFD is a Draft whose schema landed as **unstable on 30 September 2026**. The reference Claude adapter already emits message names from an earlier draft ([Subagents RFD](https://agentclientprotocol.com/rfds/subagents); [schema CHANGELOG](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/schema/v1/CHANGELOG.md); [claude-agent-acp](https://github.com/zed-industries/claude-agent-acp)). The same RFD forbids clients from adding parent and child costs together, and defines no subtree cost.

**ACP has no surface for managing configuration.** Nothing in the protocol creates, edits or deletes decompositions, namespaces or tool grants. Even a browser that spoke ACP would need custom `_deep_reasoner/...` methods or a REST API for the entire side panel.

The strongest case for Dean's idea deserves a fair hearing. One protocol for editors and the web is elegant. The subagent RFD's model maps almost one-to-one onto `subagent()` and `run_all()`: child sessions, arbitrary nesting, per-child cancel, and parent-to-child `session_message`. The TypeScript SDK already ships an experimental browser WebSocket stream that "uses the platform cookie jar," so cookie-based SSO would work ([typescript-sdk](https://github.com/agentclientprotocol/typescript-sdk)). Web ACP clients such as acp-ui exist, but acp-ui keeps its configuration in per-browser localStorage and does not address multiple users ([acp-ui](https://github.com/formulahendry/acp-ui)). Adopting ACP in the browser today therefore means tracking two drafts at once (transport and subagents) with no web renderer for the tree, while the team builds the replay, auth and side-panel layers anyway. The way to honour the suggestion without that cost is to model deep_reasoner's internal event schema on ACP's vocabulary, so that the `dr acp` encoder is nearly one-to-one, and to ship that adapter as a first-class surface. ACP in the browser can be revisited when the transport RFD completes and subagents stabilise, which will likely come with v2.

For the browser, **AG-UI 1.0** is the better-matched standard today. Its 1.0 pull request merged on 17 September 2026, and the `@ag-ui/*` packages reached 1.0.1 on 29 September ([PR #2774](https://github.com/ag-ui-protocol/ag-ui/pull/2774); [release](https://github.com/ag-ui-protocol/ag-ui/releases/tag/release/2026-09-29)). Version 1.0 adds `SUBAGENT_STARTED`, `SUBAGENT_FINISHED` and `SUBAGENT_ERROR` events carrying `parentSubagentRunId` and `parentToolCallId`, plus a `subagentRunId` attribution field on most other events. It also has reasoning events, JSON-Patch state deltas, and run outcomes that distinguish success, interrupt (pausing for human input) and cancellation ([AG-UI events](https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/docs/concepts/events.mdx)). It is MIT-licensed and transport-agnostic (SSE or WebSockets), with TypeScript, Python and .NET SDKs generated from one schema ([ag-ui repo](https://github.com/ag-ui-protocol/ag-ui)). On the rendering side, assistant-ui's docs say its AG-UI runtime assembles sub-agent transcripts under the tool call that spawned them, nesting "recursively up to sixteen levels deep" ([assistant-ui multi-agent](https://www.assistant-ui.com/docs/tools/multi-agent)). That claim was seen only in search snippets, so the first spike must confirm it. The caveats are real: 1.0 is two weeks old and was a breaking release, governance is led by CopilotKit rather than a foundation, and dollar cost has no standard field, so per-node cost must travel in `CUSTOM` or `STATE_DELTA` events. Pydantic AI's `AGUIAdapter`/`UIEventStream` split is a good Python reference for encoding events produced outside the HTTP request handler, which is exactly deep_reasoner's situation ([Pydantic AI UI](https://raw.githubusercontent.com/pydantic/pydantic-ai/main/docs/ui/overview.md)).

The table shows how the structlog events deep_reasoner already emits would map onto both encoders.

| deep_reasoner signal (already emitted) | Browser: AG-UI 1.0 | Editors and OpenHands: ACP v1 |
|---|---|---|
| `agent.start` (node_id, ancestry, namespace, depth) | `SUBAGENT_STARTED` with `subagentRunId` = node, `parentSubagentRunId`, `parentToolCallId` = the spawning cell | Stable: a `tool_call` titled "subagent: …" plus `_meta.deep_reasoner.{agentId, parentAgentId, depth}` on every update. Optionally the unstable `subagent_update` |
| `agent.turn`, then the `llm.call` response (think + code) | Reasoning and text chunks tagged with `subagentRunId` | `agent_thought_chunk` |
| `repl.execute` (code + observation) | `TOOL_CALL_START/ARGS/END` + `TOOL_CALL_RESULT` | `tool_call` of kind `execute` + `tool_call_update` (text content; `completed` or `failed`) |
| `FinalAnswer` / `agent.end` (done, failed, exhausted) | `SUBAGENT_FINISHED.result`; `RUN_FINISHED` at the root | `agent_message_chunk` + `stopReason` |
| `claude.call` cost_usd, `llm.call` usage | `CUSTOM` or `STATE_DELTA` on the tree (self + subtree) | `usage_update.cost` (session total) + `_meta` subtree breakdown |
| Decompositions, namespaces | Ordinary app UI over REST | `available_commands_update` and `configOptions` (list and select only) |

One ordering detail in the current code matters for both encoders. `repl.execute` and `llm.call` are logged only *after* the cell or call finishes (`deep_reasoner/v2/repl_coro.py`, `deep_reasoner/v2/llm_coro.py`). A child agent's `agent.start` therefore arrives before the cell that spawned it has been reported. The clean fix is a one-line `repl.start` event that carries a cell id and is emitted before execution. The UI can then show a cell as running and attach children to it by explicit id. The tree must never be reconstructed from timing. Claude Code's own VS Code agent map attaches nested sub-agents to the wrong parent for exactly that reason ([claude-code #98118](https://github.com/anthropics/claude-code/issues/98118)), and deep_reasoner's `node_id` plus ancestry already avoids the problem.

## Six stacks compared; a thin custom app wins on fit

| Option | Multi-user + UW sign-in | Per-user keys | Who runs model code | Agent tree in chat | Custom side panel | License, churn | Verdict |
|---|---|---|---|---|---|---|---|
| **A. OpenHands Canvas + agent-server, deep_reasoner as a Custom ACP agent** | No. One shared key per backend; per-user means one agent-server each, routed by you | Per backend, exported as env vars | deep_reasoner (Daytona) | Flattened; sub-agent structure dropped | Left-rail beta "App" page only | MIT; very high churn | Good localhost trial, poor hosted base |
| **B. OpenHands with a custom `AgentBase` or a forked Canvas** | As A | As A | As A | Only with a fork | Only with a fork | MIT; a fork of weekly-released code | Not recommended |
| **C. LibreChat or Open WebUI, with deep_reasoner as an OpenAI-compatible model** | Yes (OIDC/SAML/LDAP) | Yes (`user_provided`, encrypted per user) | deep_reasoner (Daytona) | Collapsed into one message | Fork required | MIT (Open WebUI: branding clause above 50 users) | Fast demo, dead end for the tree and panels |
| **D. Custom app: FastAPI + AG-UI 1.0 + assistant-ui (recommended)** | Built: SSO via reverse proxy | Built: envelope-encrypted broker | Daytona only, enforced by policy | Native nested threads (to verify) | Native | MIT parts; AG-UI 1.0 is new | Best fit; the team owns operations |
| **E. Custom app speaking ACP to the browser** | Built | Built | Daytona | Custom renderer; unstable subagent schema | Custom `_` methods or REST | Two draft specs | Viable later, premature now |
| **F. Chainlit** | Header/OAuth auth | Built | Daytona | Nested steps | Limited | Apache-2.0; community-maintained, recent CVEs | Quick internal prototype only |

LibreChat is the strongest off-the-shelf multi-user app. It is MIT-licensed, has about 45k stars, supports OAuth2/OIDC/SAML/LDAP sign-in, offers per-user `user_provided` keys and resumable streams, and shipped v0.8.8 on 30 September 2026 ([LibreChat](https://github.com/danny-avila/LibreChat); [custom endpoints](https://www.librechat.ai/docs/configuration/librechat_yaml/ai_endpoints)). But any chat app that treats deep_reasoner as an OpenAI-compatible "model" collapses the live tree, per-node cost and structured human-in-the-loop into one assistant message, and pushes the side panel into a fork.

The other options each carry a specific blocker. Since v0.6.6, **Open WebUI's** license forbids removing its branding for deployments with more than 50 users in a rolling 30 days unless an enterprise license is bought ([LICENSE](https://raw.githubusercontent.com/open-webui/open-webui/main/LICENSE)). **Chainlit's** original team stepped back on 1 May 2025, and its v2.12.0 was a security release fixing command-injection and SSRF CVEs ([Chainlit](https://github.com/Chainlit/chainlit); [releases](https://github.com/Chainlit/chainlit/releases)). **A2A** is an agent-to-agent protocol with deliberately opaque tasks. It suits a later "publish this namespace as an agent" feature, not the UI ([A2A spec](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)). The **Vercel AI SDK's** UI message stream is well specified, and its `data-*` parts, which the client reconciles by id, suit a live tree panel. But nesting is custom work there, and the format went through v5, v6 and v7 in about fifteen months ([stream protocol](https://raw.githubusercontent.com/vercel/ai/main/content/docs/04-ai-sdk-ui/50-stream-protocol.mdx)). **CopilotKit** is the natural fallback if assistant-ui disappoints, but its sub-agent grouping UI was still an open pull request on 30 September ([PR #7444](https://github.com/CopilotKit/CopilotKit/pull/7444)).

Option D wins because the distinctive parts are custom work in *every* option: the live tree, the code cells, the decomposition and namespace panels, and "save this run as an example". What off-the-shelf products supply is the smaller and more standardised part. Sign-in is reverse-proxy configuration. Key custody follows a well-documented envelope-encryption pattern. History is a table. D puts the team's effort where the research value is and keeps every dependency MIT-licensed or the team's own. Its cost is that a research team operates a service holding other people's keys, which is why the next section is mostly about boundaries.

## One server owns identity, keys, runs and history

The architecture keeps deep_reasoner's core untouched and wraps it in a handful of small services. Every user-facing protocol is an encoder over one event log that the server owns.

```
Browser SPA (React + assistant-ui: chat with inline tree, history list, side panel)
   │  AG-UI over SSE (run events, replay by after_seq)     REST/JSON (configs, keys, history)
   ▼
UW sign-in reverse proxy (Shibboleth/SAML or OIDC)        [localhost: per-launch token + Origin check]
   ▼
App server (FastAPI) ───── Store: users, config rows (YAML + versions/labels), conversations,
   │                              events(seq), key ciphertext, audit   [SQLite → Postgres]
   │ spawn / cancel / JSONL event stream
   ▼
Spawner ──► Per-user worker container (gVisor)            Credential broker (KMS/Vault-wrapped keys;
             deep_reasoner core + EventBridge processor     loopback LLM proxy that injects keys)
             `claude -p` subprocesses (Claude backbone) ───────► via ANTHROPIC_BASE_URL / base_url
             │ websocket relay (JSON only)
             ▼
           Daytona sandbox in the user's own Daytona org (no keys inside)

`dr acp` (stdio ACP agent) ──► Zed, JetBrains, OpenHands Agent Canvas (local use)
```

| Component | Responsibility | Build or reuse |
|---|---|---|
| Web SPA | Conversation list, chat with inline agent tree and code cells, side panel for namespaces, decompositions, tools and keys | React + assistant-ui (AG-UI runtime); CopilotKit as fallback |
| App server | Sessions, REST CRUD, run lifecycle, AG-UI stream with `after_seq` replay, quotas | FastAPI; Pydantic AI's AG-UI adapter as reference |
| Store | Config rows holding YAML, versions and labels, conversations, event log, key ciphertext, audit | SQLite (WAL) for the pilot; Postgres once there is more than one app process |
| EventBridge | structlog processor that turns events into canonical JSON with sequence numbers and explicit parent ids | New, modelled on `ProgressView` |
| Worker | Runs one user's conversations; Stop means kill | deep_reasoner core plus small hooks |
| Credential broker | Decrypts keys and injects them into outbound LLM calls; never returns them | Small service; Envoy `credential_injector` or LiteLLM as alternatives |
| Sandboxes | Execute every line of model-written code in hosted mode | Daytona (already supported); E2B or Modal as fallbacks |
| `dr acp` | ACP stdio agent for editors and Agent Canvas | Python `agent-client-protocol`, version pinned |

### Plugging into deep_reasoner without touching its core

The integration seam already exists. `ProgressView` in `deep_reasoner/progress.py` is a structlog processor that builds a live agent tree from `agent.start/turn/end` and `claude.call`, and it "returns every event untouched." An `EventBridge` processor installed the same way can serialise those events, together with `llm.call` and `repl.execute`, into a canonical JSON stream. Each event carries a per-conversation sequence number, node id, parent id and namespace. The worker sends that stream to the app server, which appends it to an `events` table and fans it out to the encoders. Configuration needs only a thin adapter. Calling `build_registry(inline=[NamespaceConfig.model_validate(yaml.safe_load(row.yaml)), ...])` from `deep_reasoner/namespaces.py` turns a user's database rows into a registry, so stored YAML stays byte-compatible with today's config files and the CLI keeps working. Two tools need storage decisions in hosted mode. The `kg` tool persists per namespace, so its files must live under a per-user path. The `rag` tool's in-memory chromadb resets with each worker, which is acceptable for a beta.

Four properties of the current core shape the server around it. **Runs do not stream turns or tokens, and LLM calls are non-streaming**, so the UI's unit of progress is the step: "turn 3 started", then the think-and-code text, then the observation. Running indicators and an "N sub-agents running" badge carry the experience, not a typing effect. **There is no cancellation and no timeout for in-process snippets**, so each user's runs should live in a separate worker process, where Stop and wall-clock limits work by killing the process. **Resuming a conversation works only in memory, and nothing reloads a run from its YAML logs.** The `events` table therefore becomes the system of record. The server either keeps a conversation's worker alive with an idle timeout or rebuilds the agent's message history from stored events. Rebuilding is the one substantial core feature to add, and it also makes server restarts safe. Finally, **cost accounting covers only Claude spend** (`claude.call` with `cost_usd`), so chat-backbone cost must be computed from `llm.call` usage and a price table, and labelled as an estimate. Beyond rehydration, the only core changes worth making are the `repl.start` event and run-level limits on wall-clock time and fan-out.

### Security boundaries: a breach should cost one user, not everyone

The governing principle is that any compromise should expose at most one user's own keys and data. deep_reasoner has already moved the most dangerous act, running model-written code, into Daytona. What remains is host-side containment, identity and key custody, enforced by four rules in hosted mode.

**First, only the `daytona_context` and `daytona_sandbox` REPL backends are allowed.** `local` is plain `exec` inside the server process. RestrictedPython's own package metadata says it "is not a sandbox system or a secured environment" ([RestrictedPython](https://pypi.org/pypi/RestrictedPython/json)).

**Second, tools come from a curated catalog:** `llm`, `claude_code`, `rag`, `kg` and `safe_url`. User tool factories are arbitrary Python that would run on the host. In hosted mode, "manage your own tools" therefore means granting and configuring catalog tools, not uploading code, until user tools can execute inside the sandbox.

**Third, every `claude` process runs inside the user's own worker container.** The Claude backbone's `--allowedTools "Bash(dr repl exec:*)"` pre-approves one command. But Anthropic warns that the Bash permission system "is a permission gate, not a sandbox" ([Secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)), and the `claude_code` worker tool is broader still. Inside the container, apply Anthropic's multi-tenant settings. Give each tenant its own `CLAUDE_CONFIG_DIR` and working directory, and set `setting_sources=[]` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, because auto memory "loads into the system prompt regardless of `settingSources`". Use `--tools` or `--restricted` to strip built-ins the backbone does not need ([Hosting](https://code.claude.com/docs/en/agent-sdk/hosting); [CLI reference](https://code.claude.com/docs/en/cli-reference)). For the container itself, Anthropic says gVisor's extra isolation "is often worth the overhead" for multi-tenant use. It shows hardened flags: `--cap-drop ALL`, `--read-only`, `--pids-limit`, memory caps and a non-root user. The web app must never hold the Docker socket. Workers should come from a small separate spawner, or from the Kubernetes agent-sandbox project with gVisor or Kata if UW offers a cluster ([agent-sandbox README](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-workspace/openhands/workspace/agent_sandbox/README.md)).

**Fourth, keys never enter a model-reachable environment.** With bring-your-own keys, a leaked key spends the user's own money, which makes this the single most important control. OWASP's guidance gives the practices. Encrypt keys at rest with AES-256-GCM data keys, wrapped by a KMS or Vault Transit key that never sits on the database host. Never log keys, mask them after entry, audit every use, and let users delete or replace them at any time ([OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Keys are decrypted only in the credential broker, which acts as a loopback LLM proxy. Claude Code reaches it through `ANTHROPIC_BASE_URL`, and the chat backbone through its OpenAI-compatible base URL, so "the agent never sees the actual credentials" ([Secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)). Nothing secret goes into a Daytona sandbox. In April 2026 Daytona disclosed that its own API credential could be read from inside sandboxes through passwordless sudo, giving access "to the rest of the org's sandboxes" ([Daytona advisory](https://www.daytona.io/dotfiles/updates/security-advisory-api-credential-exposure-in-sandboxes)). Its newer Secrets feature substitutes placeholders at an outbound proxy for the rare case where sandbox code needs a credential ([Daytona Secrets](https://www.daytona.io/docs/en/secrets/)). Free-tier egress limits are no safety net. Tier 1 and 2 sandboxes are restricted to an "essential services" list that users cannot override, yet it includes GitHub, `*.vercel.app`, `*.herokuapp.com` and S3, all usable exfiltration channels ([network limits](https://github.com/daytonaio/daytona/blob/v0.190.0/apps/docs/src/content/docs/en/network-limits.mdx)).

Provider policies settle the bring-your-own-key design. **Claude:** bring-your-own API keys is the compliant path. Anthropic's Commercial Terms allow hosted products to run Claude Code or the Agent SDK on three conditions. The binary must be unmodified, its sign-in methods must not be removed, and the operator must not "pay for, resell, or intermediate Claude usage on their end users' behalf" ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). The hosted beta must not offer claude.ai subscription login or accept pasted subscription tokens, because developers "may not collect, store, or intermediate Claude.ai credentials or session tokens." Anthropic enforced this against third-party tools during 2026 ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/); [claude-mem #1826](https://github.com/thedotmack/claude-mem/issues/1826)). If UW ever wants to pay for Claude usage centrally, ask Anthropic first: the published text does not clearly separate an Agent-SDK product from one that shells out to `claude -p`. Branding such as "deep_reasoner, powered by Claude" is allowed; naming a feature "Claude Code" is not ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)).

**OpenRouter:** OAuth PKCE mints a key in the user's own account in one click, so users never copy a raw key ([OpenRouter PKCE](https://openrouter.ai/docs/guides/overview/auth/oauth)). If UW later funds a free tier, provisioning keys with per-key monthly limits are the clean path ([management keys](https://openrouter.ai/docs/guides/overview/auth/management-api-keys)).

**Daytona:** ask users for a dedicated key in their personal organization with an expiry date, scoped to `write:sandboxes` and `delete:sandboxes`, plus snapshot scopes if deep_reasoner builds its image there. Rate limits and quotas are per organization, so bring-your-own keys also spread load across users' own tiers ([API keys](https://github.com/daytonaio/daytona/blob/v0.190.0/apps/docs/src/content/docs/en/api-keys.mdx); [organizations](https://github.com/daytonaio/daytona/blob/v0.190.0/apps/docs/src/content/docs/en/organizations.mdx)). Runs should use ephemeral sandboxes with short auto-stop; the default is 15 minutes ([sandboxes](https://github.com/daytonaio/daytona/blob/v0.190.0/apps/docs/src/content/docs/en/sandboxes.mdx)). The server adds its own caps on turns, wall-clock time, fan-out and concurrent sandboxes.

With bring-your-own keys, tokens and sandbox compute bill to users, so **UW's exposure is the host**. Anthropic suggests "1 GiB RAM, 5 GiB disk, and 1 CPU per agent" as a starting point. It notes that token cost typically exceeds container cost "by an order of magnitude or more" ([Hosting](https://code.claude.com/docs/en/agent-sdk/hosting)). deep_reasoner multiplies that per-agent footprint, because every Claude-backbone node is its own `claude` subprocess and one `run_all` can start many at once. With the chat backbone and Daytona, by contrast, the host only orchestrates HTTP calls. Plan capacity on peak concurrent agents, not registered users; OpenHands' enterprise sizing guide draws the same lesson for sandboxes ([Sizing Guide](https://docs.openhands.dev/enterprise/sizing-guide)). Requiring NetID sign-in before anyone can enter a key is a cheap gate against free-account abuse of the shared host.

### Storage that keeps YAML canonical

The hosted server should use one database with a `user_id` on every row rather than a SQLite file per user. Per-user files isolate well and make "delete my data" a single unlink, but they complicate sharing, forking and admin queries ([per-user SQLite vs row-level](https://dev.to/helperx/multi-tenant-data-isolation-in-sqlite-per-user-database-files-vs-row-level-5glm)). Open WebUI's experience is that SQLite suffices for one process, but "for any multi-user or high-concurrency setup, PostgreSQL is mandatory" ([Open WebUI scaling](https://docs.openwebui.com/getting-started/advanced-topics/scaling/)). Each namespace and decomposition row stores the **canonical YAML text** plus indexed metadata: owner, name, version, label, parent and visibility. That honours "YAML behind the scenes" literally. Versions are immutable. Namespaces reference a movable `current` label, and every run records the exact versions it used, following the versioning pattern of evaluation tools such as Langfuse ([Langfuse versioning](https://langfuse.com/changelog/2025-12-15-dataset-versioning)). Export and import should use YAML bundles that carry a format version and have secrets stripped, with tool grants naming credentials rather than containing them. Exports should pass the same permission check as reads; Dify's CVE-2025-32790 let ordinary users export app definitions only admins should have seen ([advisory](https://github.com/langgenius/dify/security/advisories/GHSA-jp6m-v4gw-5vgp)). Three hosted agent-builders have shut down or announced shutdown within about 14 months, starting with Humanloop ([HN](https://news.ycombinator.com/item?id=44592216)). That is reason enough to keep the format plain and exportable. The localhost variant uses one SQLite file with two-way sync to the existing config directory.

### A side panel built from proven patterns

Authoring tools across vendors have converged on one loop: describe, get a draft, edit it in a form, try it in a preview. They are moving away from node canvases for behaviour the model decides. OpenAI is reported to be retiring its graph-based Agent Builder on 30 November 2026 ([The Rundown](https://www.therundown.ai/tools/agent-builder), secondary).

For deep_reasoner, the main path should be **"Save this run as a decomposition"**. The user picks the turns to keep and trims dead ends, elides long observations, keeps each sub-agent spawn as a single cell plus its result, and saves the result as a new version. This adapts LangSmith's and Langfuse's "add to dataset" to a trace that already has the shape of a decomposition, which avoids the fidelity bugs those tools have documented ([LangSmith datasets](https://docs.langchain.com/langsmith/manage-datasets-in-application); [langfuse #3912](https://github.com/langfuse/langfuse/issues/3912)). The editor shows chat-style cards (task, think, code, observation, FinalAnswer) with a "View YAML" toggle and flags observations edited by hand. Each decomposition carries a Skills-style "use when…" description ([Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)) and a switch for "run literally as the opening program" (`--main-decomposition`).

Namespaces appear as a tree matching their dotted names. Each field shows a Google-Admin-style badge ("Inherited from research" or "Overridden here") with Override and Reset buttons ([Google Admin](https://support.google.com/a/answer/2655363?hl=en)), and an "effective config" view shows where every value comes from. Tool grants are a checklist on which a child cannot re-enable a tool its parent denies. The spawn allow-list is a "Can delegate to" checklist beside a read-only diagram. Before saving, a split preview runs the draft against three to ten test tasks and shows a matrix of tasks by version ([promptfoo](https://www.promptfoo.dev/docs/intro/); [Anthropic Console evaluate](https://www.anthropic.com/news/evaluate-prompts)). The matrix directly counters non-experts' tendency to generalise from one lucky run ([Why Johnny Can't Prompt](https://dl.acm.org/doi/pdf/10.1145/3544548.3581388)).

### The localhost variant is the same app with the brakes moved

`dr serve` launches the same FastAPI app and SPA, bound to 127.0.0.1, with one SQLite file. Any web page the user visits can try to reach a local server that executes code. So copy Canvas's pattern, a loopback-only listener with a session key injected at each launch, and add an Origin check ([OpenHands README](https://github.com/OpenHands/OpenHands/blob/main/README.md)). Serve nothing else on the same origin: OpenHands found that its co-hosted VS Code could read the session key from localStorage ([SELF_HOSTING.md](https://github.com/OpenHands/OpenHands/blob/main/docs/SELF_HOSTING.md)).

Local file access is the point of this variant. The `local` REPL backend gives the agent the user's file system. It should come with an explicit warning, as OpenHands' own no-sandbox mode warns that "the agent will have full access to your filesystem!" It should also use a chosen project folder as the working directory and offer Daytona or `restricted` as the cautious options. Keys come from environment variables or the OS keychain. For Claude, document API keys. A personal subscription login on the user's own machine is closer to "ordinary, individual usage," but Anthropic's April 2026 enforcement hit third-party harnesses running locally, so it stays at the user's own risk. `dr acp` then lets the same user drive deep_reasoner from Zed, JetBrains or Agent Canvas with no extra server.

### Risks worth tracking from day one

| Risk | Why it is real | Mitigation |
|---|---|---|
| Model code or a `claude` process reaches another user's keys or data | `local` is in-process exec; RestrictedPython is not a sandbox; Bash allow rules are "a permission gate, not a sandbox" | Daytona-only hosted policy; per-user gVisor workers; keys injected by the broker; no user Python tools on the host |
| Leaked keys cost users money | Free-tier sandbox egress still reaches GitHub, S3 and Vercel; Daytona's own credential bug in April 2026 | Keys never in sandboxes, logs or the browser; scoped, expiring provider keys; audit log and one-click revoke |
| Runaway runs | No cancellation or snippet timeout in the core; Claude's `max_budget_usd` stops on a "client-side cost estimate" ([Python SDK](https://code.claude.com/docs/en/agent-sdk/python)) | Workers that can be killed; server caps on turns, wall clock, fan-out and concurrent sandboxes; nudge users to set provider-side limits |
| Protocol churn | AG-UI 1.0 is two weeks old; ACP subagents are unstable and v2 is a draft | Canonical internal events; thin, replaceable encoders; pinned SDK versions |
| Daytona vendor risk | Closed-source since June 2026, with the last AGPL release unmaintained ([daytona README](https://github.com/daytonaio/daytona)); isolation is Sysbox containers sharing the host kernel despite "dedicated kernel" marketing ([security exhibit](https://github.com/daytonaio/daytona/blob/v0.190.0/apps/docs/src/content/docs/en/security-exhibit.mdx)) | Keep the REPL backend interface; E2B's Apache-2.0 Firecracker runtime ([e2b infra](https://github.com/e2b-dev/infra)) or Modal as fallbacks |
| Provider policy shifts | Anthropic enforced against third-party harnesses in 2026 | API keys only; no hosted subscription login; plain-text "powered by Claude" |
| Long-lived streams through UW proxies | No experience reports were found for multi-minute SSE behind university load balancers | Keep-alives; `after_seq` replay from the events table; runs independent of any HTTP request |
| Host capacity | Each Claude-backbone node is a subprocess (~1 GiB suggested), and `run_all` fans out | Per-user concurrency caps; chat backbone as the default early on |
| Operating burden | A research team becomes custodian of other people's credentials | Closed beta first; review by UW's security office; smallest possible attack surface |

### Decisions the team must make, and what each hinges on

| Decision | Options | Lean | Hinges on |
|---|---|---|---|
| Browser event protocol | AG-UI 1.0; ACP over WebSocket; own JSON over WebSocket | AG-UI, with the canonical log independent of it | Whether assistant-ui renders a deep, concurrent recorded tree well in Phase 0 |
| Host-side isolation | One shared process; per-user container; per-run container | Per-user gVisor container (limits any breach to one user) | Whether UW provides a VM that can run gVisor or a Kubernetes cluster; the team's operating capacity |
| Claude backbone in the hosted beta | From day one; after isolation is proven; never | Start with the chat backbone + Daytona; enable Claude once per-user workers are proven | The isolation decision and host capacity |
| User-authored tools | Never hosted; run inside the sandbox; via MCP over HTTP | Catalog only in Phase 2; revisit later | Whether tool code can run sandbox-side through the relay |
| Who pays | Pure bring-your-own; UW-funded caps (OpenRouter provisioning keys); research credits | Pure bring-your-own for the beta | UW budget; Anthropic's answer on central funding |
| Store | Shared DB with `user_id`; one SQLite file per user | Shared DB: SQLite for the pilot, Postgres when scaling | How much sharing and concurrency the team expects |
| List inheritance semantics | Append or replace; whether a child can remove inherited items | Append with explicit remove; a tool deny always wins | Usability testing with UW users (no published evidence found) |
| Conversation persistence | Keep the worker alive; rebuild from events | Rebuild from events (also makes restarts safe) | Effort of the core change |
| Sign-in | SAML via Shibboleth; OIDC | Whatever UW IT supports, as reverse-proxy header auth | UW IT (OIDC availability unverified) |
| OpenHands' role | Ignore; alternative local UI; Enterprise license | Alternative local UI via `dr acp` only | Whether All Hands offers academic licensing |

## Conclusion

The question of building versus piggybacking is really a question of where the security boundary sits. deep_reasoner has already put its most dangerous act, executing model-written code, behind Daytona. What is left is identity, key custody and containment of host-side orchestration. Those pieces are small, standard and well documented, and they are precisely the pieces OpenHands keeps behind a commercial license. Piggybacking would add a weekly-changing dependency without removing that work. Owning a thin server, by contrast, buys a single event log that becomes the product's spine. That log drives live rendering, reconnect replay and cost, and above all the "save this run as a decomposition" path that no existing product offers for code-bearing transcripts.

The protocol debate also shrinks once that log belongs to deep_reasoner. ACP and AG-UI become thin, replaceable encoders, so either bet is reversible within weeks, and Dean's ACP adapter earns its place as the editor and OpenHands surface rather than the browser wire. What will actually decide whether the beta succeeds is less the wire format than three unglamorous gaps in the core: cancellation, conversation persistence and a cell-start event. Beyond those, it depends on whether non-expert UW users can turn a run into an example they trust. The most valuable early experiment is therefore not a protocol shoot-out but watching a few users save, edit and re-test a decomposition in the Phase 1 localhost app.
