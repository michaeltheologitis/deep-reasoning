# deep-reasoning

A minimal chat for `deep_reasoner`, in one browser tab: chats on the left, the conversation on the right, and each run's sub-agents as a tree that clicks open and shut, in the look of Claude Code.

Read `../coding-skills/GUIDE.md` and follow it; in the main session a hook has already printed it.
This project's Notion page (todos, changelog, notes): https://app.notion.com/p/40362fb222378153b3a4edba29ea4329. The brief under its Notes is the whole context for the current work.

## Goals and non-goals

- The UI is agreed: the clickable prototype of PR #73. v1 built it for real, in five PRs: (1) the app shell; (2) the Library in `library.sqlite`; (3) runs: `deep_reasoner` in a subprocess, steps streamed live, Stop ends the tree, costs per call; (4) chats saved in `chats.sqlite`; (5) the UI wired to real data.
- The page reads chats and runs from the API. `src/deep_reasoning/web/fold.js` folds a run's events into the tree the chat draws, the same for a saved turn and a live one, walking a node's ancestors once each, as a shared file may name a node its own ancestor; a `library.change` is a step of the agent that made it, after its cell, and is listed on the turn (`turn.changes`, each with the tasks above it) for the lines under the answer; a live run streams over SSE from `?after=` the last seq the page has, so a reload catches up without gaps or repeats.
- The server listens on 127.0.0.1 only, and refuses requests naming another host or sent from another site's page (their `Origin`).
- The Library file is the app file: one SQLite file (default `~/.deep-reasoning/library.sqlite`, `--library PATH` for another) holding the Library (every namespace, decomposition and custom tool's Python source, and the run settings, each as the engine's own YAML), the chats with their runs' events, and the app's settings. Latest only: sharing or copying the file is the snapshot of all of it, but not the keys or the runs' working folders, and deleting it (`deep-reasoning reset`, with its data folder) starts afresh. A shared file is a trust boundary: what is read from it is checked (each custom server as `add_server` checks one, and not under another provider's name or key variable; each setting's shape; each chat's id and folder; each run's id, as it names a folder; each event row, which must load to an object with its seq, a time and a kind and no number past ±2**53, and a run's turn.start with its prompt), and what fails is left out with a warning, so it reads as unset. Deleted rows are wiped (`secure_delete`), and the file's own triggers and views never run (`setconfig`), so a copy carries nothing deleted. A Library file that can't be written (read only, full, busy) answers 400 in plain words; any other SQLite error is a bug and stays a 500. Each file's run folders and scratch folders are in its data folder, `files/<first 16 hex of the sha256 of its real path>/` in the app's home (`folders.data_folder`), so a copy never shares them with the original and a moved file starts afresh, deleting nothing. Schema version 3 (`PRAGMA user_version`); a version-1 file (the Library alone) or version-2 file (no runs) opens and gains the tables it lacks, keeping what it holds; any other file is refused untouched. `src/deep_reasoning/library.py` is the Library's store and lays the whole file out; `engine_config()` turns it into the config dict `V2Config` reads at run start, with only the tools some namespace grants (and the app's own). The engine builds every tool a config declares, whichever namespace the run enters (only which agents see a tool is per namespace), so once any namespace grants a tool, its module and factory run at the start of every run of every chat, and one that fails to build stops every chat until no namespace grants it (the panel lists every tool, granted or not); a tool no namespace grants never runs. It holds no model or client: each chat picks its model, and an older file's are left unread. `deep_reasoner` is never changed for it. The panel adds, edits and deletes namespaces (the API's `/api/namespaces`), each change checked by the engine's `NamespaceConfig` and `registry.check` over the whole Library in one transaction; a chat whose namespace was deleted is refused on its next run until it picks another. Each decomposition's turns are checked as a worked example (`turn_problems`, by the rules the engine's own docs/configs examples keep: the task first, after any system turns; turns alternating; each assistant turn a `<think>` and one `<repl>`; after a cell that didn't call `FinalAnswer`, its `<observation>`; `FinalAnswer` last), its code not run; problems never refuse one, so a draft is stored: the Decompositions tab marks each ✓ or ✗ with them, `panel()`, `library.show()`, the POST and `write_decomposition` return them, and the add form warns with them as you type through `web/turns.js`, its twin, held to its words by `tests/turn_cases.json`.
- Keys live in `.env` in the app's home, readable only by the user (0600), and nowhere else: never in the Library, chats, run folders, events, logs or responses (a provider's key that a cell prints, the run's own or any provider's key variable set in the shell, is withheld from its events as `[key withheld]`, unless shorter than 8 characters, as no secret; other secrets a cell reads from the shell travel with the file); the page gets only a status per provider (`set`, `shell`, `none`). A key saved there wins over the shell's. A custom server's key, saved or from the shell, goes only to the address it was saved for, recorded beside it in `.env` (`DEEP_REASONING_<NAME>_URL`). Typing a key for a server records its address; with no key typed, adding a server records it only while no other address holds the name, and changing a server's URL moves it only when it was that server's. A server of that name at another address, as a shared file may hold, has no key ("none"), even after Save, until a key is typed for it, which rebinds the name; removing it leaves the user's key alone. The known vendors, their addresses and the few current models the model menu features for each (strongest first, checked against each vendor's models page on the date its comment names; typing searches the vendor's whole `GET /models`) are `VENDORS` in `src/deep_reasoning/settings.py`; custom servers (any OpenAI-compatible URL), the model picked last and the default folder are in the app file's `app_settings` table (key, JSON), apart from the Library's `settings` table, which is the run settings. A run's config is `engine_config()` with the chat's model and its provider's `base_url` and `api_key_env` put in, and the key reaches the worker in its environment only. Never `ANTHROPIC_API_KEY`: Anthropic's key is `DEEP_REASONING_ANTHROPIC_KEY`, and the worker never gets `ANTHROPIC_API_KEY`.
- Chats are in the app file's `chats` table: each chat's id, title, when it was made, and its namespace, model (with the provider that serves it) and working folder, from its next message. `src/deep_reasoning/chats.py` is the store. A chat's turns are its runs, in the same file (`src/deep_reasoning/runs.py`): the `runs` table names each run's chat, and `events` holds each event as the JSON the page folds, saved as it happens, one commit each on the event loop, in WAL mode with `synchronous=NORMAL` so no event waits on an fsync. The `-wal` and `-shm` files beside the file exist while a run is going and fold back when it ends, so a copy made with the app stopped is whole. Deleting a chat deletes its runs' events, and the next start deletes those of a chat deleted before its runs were; a run the app stopped under, with no `turn.end`, is ended failed when the app next starts, and one it can't end (unreadable, or a file it can't write) is left as it is and reads back failed; an event the file refuses (full, read only) ends its run failed, its streams still get the `turn.end`, and the chat takes its next message. An older `chats.sqlite`, `settings.json`, `runs/` or `work/` directly in the app's home is left untouched and unread, until `reset` of the default file deletes it.
- Each chat has a working folder (`src/deep_reasoning/folders.py`): the worker's cwd, where the agent's Python reads and writes files, so a file from one message is there for the next. It is the folder the user chose (typed, or browsed through `GET /api/folders`; new chats start in settings' default folder while it exists, so a default from another computer gives them their scratch folder), or the chat's scratch folder `work/<chat>/` in the file's data folder, made on its first run and deleted with the chat. A chosen folder is never deleted, and deleting a chat deletes nothing but its own scratch folder. The run's working files (`spec.yaml`, `worker.log`, written tools, the engine's `run_dir`) stay in `runs/<run>/` in the data folder, scratch that a copy of the file doesn't carry. The worker starts with `python -P` and puts the folder last on `sys.path`, so the user's modules import but never shadow an installed one. A run in a folder that is gone is refused before it starts.
- The app gives the agent tools of its own, in `src/deep_reasoning/app_tools.py`, loaded through the engine's `factory_from`, so the engine never changes. Their blocks (`APP_TOOLS` in `library.py`) are added in code, never stored in the file; their names are reserved (a custom tool can't take one, and a shared file's row with one is left out with a warning), and `engine_config()` puts the app file's path, the chat id, the run id, the run's tools folder, the chat's namespace and the providers' key variables in each. Each opens the file as it is (`open_existing`, `mode=ro` or `mode=rw`, with the same trust checks), never making a moved or deleted one afresh. `history` (read-only; a fresh Library grants it at root, with a worked example there that every namespace inherits, `explain an earlier answer` in `history_example.yaml`: print `history.steps`, then answer in a later cell from what it printed; an older Library isn't changed) returns this chat's earlier runs as plain data, numbered as the recap numbers them, through a Python twin of `fold.js`. `library` (granted only in the `librarian` namespace a fresh Library seeds, `tools: [library]`, which nothing inherits; an older Library isn't changed) reads the namespaces as the panel shows them, from any namespace; adds or replaces a decomposition (`add_decomposition(..., replace=True)`); adds a namespace or changes one's own fields (`add_namespace`, `change_namespace`: its YAML as the panel's Edit YAML shows it, so `system_suffix`, `vars`, `tools` and `spawn`), each with the panel's checks in one transaction, from the worker while the server saves events; and adds or replaces a custom tool (`write_tool(name, source, factory, settings=None)`, which the agent then grants with `change_namespace`): a Python name that is no keyword, built-in's (`llm`, `rag`, `kg`, `safe_url`, `claude_code`), app tool's or name the REPL binds itself (the engine's `RESERVED_NAMES`), settings of plain values (none may be `factory` or `factory_from`), source that parses (`parsed_python`, shared with import and the panel: refused with its line, or as too deep), then built as a run builds it, by the engine's `make_tool` with the run's client from a folder of its own (`tempfile.mkdtemp`) under the run's `tools/checks/`, deleted after (the engine keeps each module it imported by path), refused in words with the factory's error, and stored as an import stores one (`store_tool`: its block, `factory_from: <name>.py` and its source, kept only if `accepted()`). Only in a chat whose namespace resolves to the `local` REPL, as the build runs the agent's code in the worker, outside any sandbox; never over a tool root grants (every chat would run the agent's code as one of its own) or one the engine builds from its block alone (`claude_code`, an `llm` preset: no Python to write back). The grant and these locks are checked before the build, and again under the write lock, which the build doesn't hold. It writes only in a run whose chat's namespace grants `library` through its chain, checked under the same write lock (`allowed`) before anything else, so a sub-agent spawned into `librarian` from a chat in another namespace can't, and a librarian chat's agent may hand the tool to a sub-agent elsewhere (`subagent(..., tools={...})`). It never writes root, its YAML or its decompositions; never sets or changes a namespace's `repl` or `reasoner` (`reasoner: claude_code` would bill Michael's subscription), or adds the app's own tools to a namespace's `tools` or takes them out (granting them is the user's, in the panel); adds no namespace under one whose chain grants `library` or runs Claude Code (its `registry.backbone`, or a tool whose factory is `claude_code`), so no namespace it makes can edit or bill; and grants no tool whose factory is `claude_code` that the namespace's stored tools lack (it bills the subscription as `reasoner` would; keeping or removing one is fine), each checked under the same lock against the Library as the engine reads it; has no method for the system prompt, the run settings or deleting; and never writes YAML, a tool's source or its settings as YAML over 1,000,000 characters, or a name, YAML, source or settings holding a provider's key in its text or its parsed data (a tool's string and bytes literals), which an escape can spell (the values of the key variables in the worker's environment, as `secrets_of` finds them), and takes only plain `str`. These locks are in `app_tools.py`, as the panel still edits all of it; they guard the tool, not the file, which a cell can open itself. Every refusal, a busy or unwritable file included, is a `LibraryError` in plain words. Each change is logged as `library.change` (what: `decomposition`, `namespace` or `tool`; namespace, none for a tool; name, which for a namespace is its own; before, None when added; after, as stored: a tool's row, its block's YAML, then `# <name>.py` and its source, `tool_text`, so a settings or factory change shows and writing the before back restores it), which the worker records as a run event of the calling agent's node and its open cell. The page shows each as a step in the tree and as a line under the answer, worded by `changeText` in `fold.js` ("added namespace research", "replaced tool word_count"), each opening onto its before and after YAML or source, as untrusted text only (any cell can log one, and a shared file can hold any), and on a live run's change the Library panel reads the Library afresh, keeping its drafts, and so does the namespace menu under the message box; `history.steps` lists it too. A change applies from the next message, and undoing one is asking the agent to write the before back. The design is the sub-page under the Notion page's Notes.
- No sandboxing or safety layers, and nothing from the old app's OpenHands or ACP stack.

## Checks

- `uv sync`, then `uv run deep-reasoning` serves the app at http://127.0.0.1:8000 and opens a tab (`--port` to change the port, `--no-browser` to skip the tab). `uv run deep-reasoning import CONFIG.yaml` reads an engine config into the Library. `uv run deep-reasoning reset` deletes the app file's side files, then the file, its data folder and, for the default file only, an older version's leftovers in the app's home, after listing them and asking (`--yes` doesn't ask). It refuses, deleting nothing, a path naming no file, a symlink (naming its target), a folder or anything else but a file, and a file it can't read through `open_existing(..., "ro")` as a version 1–3 Library, so nothing writes the file before the user types `delete`; it keeps `.env`, every folder a chat or the settings chose, and a folder holding one. The UI is static files in `src/deep_reasoning/web/`, no build step, served at `/`.
- `uv run pytest` (no network: the model is a fake on 127.0.0.1); `node --test tests/*.test.mjs` (the fold and the turn check, no dependencies); `uv run ruff check && uv run ruff format --check`; `node --input-type=module --check < FILE` for each of `src/deep_reasoning/web/app.js`, `fold.js`, `library.js`, `settings.js` and `turns.js` (as modules: a plain `node --check app.js` misses errors such as a name declared twice, which stop the page loading).
- `uv run pytest -m live -s` runs the gpt-6-luna live test, a paid call, and logs what it spent; it needs `OPENAI_API_KEY` (in a cloud session `OPENAI_API_KEY=placeholder`: the network proxy adds the real one).
- Check each UI change in a real browser against `uv run deep-reasoning --no-browser` (Playwright is preinstalled in cloud sessions): a new chat, a live run with its tree opened, a follow-up, a reload mid-run, Stop, rename, delete, a restart, both themes, phone width, no console errors.
- To drive the UI without a paid model: serve `tests/fake_model.py`'s `FakeOpenAI` from a process of its own on a scripted plan (`scripts/record_runs.py` has fan-outs, nested delegation and a run to stop), run `HOME=<tmp> uv run deep-reasoning --no-browser --library <tmp>/lib.sqlite`, add the fake in settings as a custom server (its `base_url`, any key), and pick one of its models under the input (`library_on` in `tests/conftest.py` does the same through `settings.py`). `HOME` keeps its keys, runs and scratch folders out of your own `~/.deep-reasoning`.
- The fold's fixtures in `tests/runs/` are real runs against the fake model, recorded from the app file, never typed: `uv run python scripts/record_runs.py`. Record them again when the worker's events change.

## Conventions

- A PR that adds or changes what a user can do updates README.md's list of what the app supports in the same PR.
- No paid model calls except the gpt-6-luna live tests, and the Claude Code on Sonnet live test through Michael's subscription token. Never set `ANTHROPIC_API_KEY`.
- Tests import copies of `deep_reasoner`'s example configs in `tests/configs/` (0.3.0's `docs/configs`, same layout); refresh them from the pinned tag, never edit them.
- Kill only the processes you started: never `pkill -f` or `pgrep -f`. `uv run` puts a Python child under its own process, so stop both (or run `.venv/bin/python` directly), and check with `ps` that nothing you started is left before you report.
- `deep_reasoner`'s repository is read-only for us: no PRs, issues or comments there. The app depends on it from GitHub, pinned to a tag in `pyproject.toml`.
- The previous app is in history at `a80bb2e` (`git show a80bb2e:<path>`), and its design docs are on the `design-docs` branch. In a shallow clone, run `git fetch --unshallow` or `git fetch origin design-docs` first.
